# Резервное копирование и восстановление

[← README](../../README.md) · [All documentation](../../README.md#documentation) · [Персональные данные](privacy.md) · [Windows](windows.md#backup-copies)

У сервиса нет базы данных, поэтому копировать нужно немного: базу знаний,
если её правят прямо на сервере, и файл настроек `.env`. Всё остальное
восстанавливается из Git или не должно сохраняться вовсе.

## Что входит в копию

| Что | Копировать? | Почему |
| --- | --- | --- |
| `data/knowledge_base.json` | Да, если правится на сервере | Менеджеры меняют цены и условия без коммита в Git; сломанная или ошибочная правка — главный риск |
| `.env` | Да, **отдельно и как секрет** | Ключ LLM, токен и секрет amoCRM, секрет вебхука, пароль менеджера |
| Код, `evals/`, документация, PDF | Нет | Восстанавливаются из Git по тегу или коммиту |
| `dist/widget.zip`, Docker-образ | Нет | Собираются заново из тега ([Версии и выпуск](../RELEASES.md)) |
| Кэш сообщений amoCRM, счётчики лимита | Нет | Живут в памяти процесса и намеренно не сохраняются ([Персональные данные](privacy.md)) |

Если база знаний меняется только через Git (коммит → выпуск), отдельная копия
не нужна: история файла хранится в репозитории.

## Копия .env — секрет

- Храните её в менеджере паролей или в зашифрованном хранилище, не в
  репозитории и не рядом с копиями базы знаний.
- Не отправляйте `.env` в чаты и письма. Если файл утёк — замените все
  ключи: сгенерируйте новый ключ LLM, новый долгосрочный токен amoCRM,
  новые `AMOCRM_WEBHOOK_SECRET` и `UI_BASIC_AUTH_PASSWORD`, затем обновите
  URL вебхука в amoCRM.

## Создать копию базы знаний

Папка для копий — вне репозитория, например `~/amocrm-backups`:

```bash
mkdir -p ~/amocrm-backups
cp data/knowledge_base.json ~/amocrm-backups/knowledge_base-$(date +%Y%m%d-%H%M%S).json
ls -l ~/amocrm-backups
```

Делайте копию **перед** каждой заметной правкой базы знаний на сервере.

## Проверить копию

Копия бесполезна, если в ней сломанный JSON. Проверьте её той же схемой,
по которой сервис загружает базу знаний:

```bash
.venv/bin/python -c "from pathlib import Path; from app.knowledge.models import KnowledgeBase; kb = KnowledgeBase.model_validate_json(Path('$HOME/amocrm-backups/<имя файла>.json').read_text(encoding='utf-8')); print(len(kb.products), len(kb.faq))"
```

Для демо-базы ожидается `10 7` — число позиций и разделов FAQ. Ошибка
`ValidationError` с путём к полю означает, что копия не подойдёт.

## Восстановить базу знаний

```bash
cp ~/amocrm-backups/<имя файла>.json data/knowledge_base.json
curl -s http://127.0.0.1:8000/health
.venv/bin/python scripts/run_evals.py retrieval
```

Перезапуск не нужен: сервис замечает изменение файла и перечитывает его.
Ожидается `"status":"ok"` в `/health` и `Результат: PASS` у оценки поиска.

В Docker папка `./data` смонтирована в контейнер только для чтения:
восстанавливайте файл на хосте, в папке проекта, — контейнер увидит его сразу.

Если сервис не запускается из-за сломанного файла, восстановите копию тем же
`cp` и запустите сервис снова — см. [Восстановление после сбоев](../RECOVERY.md#сломанная-правка-базы-знаний).

## Восстановить настройки

```bash
cp <расшифрованная копия> .env
docker compose up --detach
curl -s http://127.0.0.1:8000/health
```

Настройки читаются при запуске, поэтому после замены `.env` контейнер
нужно пересоздать (`docker compose up --detach`) или перезапустить локальный
Uvicorn.

## Как это проверяется

- Загрузка базы знаний и поведение при сломанном файле — тесты
  `test_knowledge_base_reloads_after_edit` и
  `test_broken_edit_keeps_last_valid_version`.
- 27 октября 2026 года полный круг выполнен на запущенном Uvicorn с
  временной копией базы знаний (`KNOWLEDGE_BASE_PATH`): проверка копии —
  `10 7`; после порчи файла `/health` → `degraded` и
  `JSONDecodeError: Expecting property name…`; после `cp` из копии без
  перезапуска → `ok`, 10 позиций.
- В Docker и на Windows круг не проверялся.
