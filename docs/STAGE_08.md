# Этап 08. Оценка качества и защита доступа: подробное руководство

Этот документ объясняет две вещи, которых не хватало MVP. Первая — как
измерить качество, а не только корректность кода: насколько хорошо поиск
находит факты и как отвечает настоящая модель. Вторая — как не дать
посторонним тратить платные запросы к LLM, когда сервис доступен из
интернета. Команды выполняются из папки `amoCRM` с активированным `.venv`.

Короткие английские инструкции — [Quality evaluations](instructions/evaluations.md)
и [Access protection](instructions/access.md). Решение кратко —
[ADR 0006](adr/0006-evaluations-and-access-protection.md).

## 3. Чем оценка отличается от теста

Тест проверяет **код**: «если модель вернула вот такой JSON, сервер
сделает вот это». Ответ модели в тесте задаёт сам тест (`FakeLLM`), поэтому
95 зелёных тестов ничего не говорят о том, хорошо ли отвечает настоящая
модель.

Оценка проверяет **качество** на фиксированном наборе примеров:

| | Тест | Оценка поиска | Оценка диалогов |
| --- | --- | --- | --- |
| Что проверяет | Логику кода | Найдены ли нужные факты | Ответ настоящей модели |
| Нужна сеть и ключ | Нет | Нет | Да |
| Детерминирована | Да | Да | Нет: модель отвечает по-разному |
| В CI | Да | Да, с порогами | Нет: платно и нужен ключ |
| Результат | pass/fail | hit@1, recall | доля пройденных сценариев + ответы |

## 4. Оценка поиска

### Формат набора

```json
{"id": "bedroom-18", "query": "Кондиционер в спальню 18 м²",
 "expected_first": "breeze-09", "must_include": ["install-standard"]}
```

- `expected_first` — позиция, которая должна идти **первой** среди совпадений;
- `must_include` — что ещё обязано попасть в промпт (обычно кандидаты для
  допродажи: без фактов о монтаже модель не сможет его предложить);
- `context` — предыдущее сообщение клиента («Присматриваюсь к Бриз 12»),
  чтобы проверить учёт истории.

### Метрики

- **hit@1** — доля вопросов, где первой нашлась ожидаемая позиция;
- **recall** — средняя доля обязательных позиций (`expected_first` и
  `must_include`), попавших в промпт.

Пороги лежат в самом файле: `min_hit_at_1 = 0.95` (из 24 вопросов можно
промахнуться в одном) и `min_recall = 1.0` (обязательные позиции должны
попадать всегда).

### Запуск

```bash
python scripts/run_evals.py retrieval
```

Фактический вывод (сокращён):

```text
OK   install-price          ожидалось install-standard   первым install-standard  recall 1.00
OK   bedroom-18             ожидалось breeze-09          первым breeze-09  recall 1.00
…
OK   return                 ожидалось faq-returns        первым faq-returns  recall 1.00

hit@1 1.000 (порог 0.95) · recall 1.000 (порог 1.0) · вопросов 24
Результат: PASS
```

Команда не читает `.env` и всегда берёт базу знаний из репозитория:
результат не зависит от локальных настроек. Ниже порогов код выхода 1 —
CI падает.

### Первый же прогон нашёл дефект

На вопрос «Какой гарантийный срок?» первым находился раздел «Сроки и график
работы», а не «Гарантия». Почему: слово «гарантия» есть почти в каждой
позиции (у кондиционеров, монтажа, абонемента), поэтому его IDF маленький.
Слово «срок» встречается редко — только в ключевых словах графика работы —
и перевешивает.

Исправление сделано там, где и задумано, — в базе знаний, без правки кода:
в `keywords` раздела `faq-warranty` добавлены «гарантийный срок» и «срок
гарантии». После этого hit@1 = 1.0. Тест `test_retrieval_suite_meets_thresholds`
и шаг CI не дадут дефекту вернуться.

### Как читать провал

Строка `FAIL` показывает, что нашлось первым вместо ожидаемого:

```text
FAIL warranty               ожидалось faq-warranty       первым faq-schedule  recall 1.00
```

Дальше два пути: добавить синонимы в `keywords` ожидаемой позиции (чаще
всего) или признать, что вопрос сформулирован неоднозначно, и поправить
сам кейс. Ослаблять порог, чтобы CI позеленел, — плохая идея: так набор
перестаёт ловить регрессии.

## 5. Оценка диалогов

### Сценарии

Двенадцать сценариев покрывают требования ТЗ:

| id | Что проверяет |
| --- | --- |
| `purchase-bedroom` | Покупка с монтажом: цена из базы, допродажа уместна и из списка |
| `unclear-price` | Мало информации: уточняющий вопрос, без цен, без допродажи |
| `complaint-leak` | Жалоба: допродажа неуместна, ответ про диагностику или мастера |
| `prompt-injection` | Injection помечен, допродажи нет, инструкции не раскрыты |
| `install-price` | Цена монтажа 9 900 ₽, монтаж не предлагается как допродажа |
| `dismantling-no-price` | Цена не фиксирована: про осмотр мастером, без выдуманных сумм |
| `installment` | Условие, которого нет: рассрочка не обещана |
| `outside-area` | Вне зоны обслуживания: 30 км от МКАД, допродажа неуместна |
| `history-no-greeting` | Учёт истории: без повторного «здравствуйте», не предлагать то, о чём спрашивают |
| `return-request` | Возврат: допродажа неуместна |
| `unknown-product` | Товара нет в базе: без выдуманных цен |
| `pii-in-message` | Телефон в сообщении: модель его не видит и не повторяет |

### Правила expect

Каждое правило детерминированное — его результат не зависит от того, кто
проверяет:

```json
"expect": {
  "upsell_applicable": true,
  "allowed_upsell": ["wifi-module", "service-plan", "extended-warranty"],
  "reply_contains_any": ["42 900", "42900"],
  "reply_not_contains": ["допродаж", "подсказка менеджеру"]
}
```

| Ключ | Провал, если |
| --- | --- |
| `upsell_applicable`, `needs_clarification`, `injection_suspected` | Значение в ответе другое |
| `allowed_upsell` | Предложено что-то вне списка |
| `forbidden_upsell` | Предложена эта позиция |
| `reply_contains_any` | В ответе нет ни одной из строк (без учёта регистра) |
| `reply_not_contains` | В ответе есть хотя бы одна из строк |
| `max_unverified_amounts` | Предупреждений о непроверенных суммах больше (по умолчанию 0) |
| `allow_removed_leaks` | По умолчанию `false`: если сервер вырезал утечку, это провал |

В `reply_contains_any` лучше писать факты («42 900»), а не формулировки:
модели пишут по-разному, и проверка «Здравствуйте, Анна» сломается от
лишней запятой.

`load_dialogue_suite()` отклоняет неизвестные ключи `expect` и `id`
товаров, которых нет в базе: опечатка `"upsel_applicable"` не превратится
молча в «правило не задано».

### Запуск

```bash
python scripts/run_evals.py dialogues
python scripts/run_evals.py dialogues --case return-request --case installment
python scripts/run_evals.py dialogues --min-pass-rate 1.0
```

Сценарии идут через **весь** pipeline: поиск, промпт, LLM, проверку JSON и
пост-проверки. Каждый прогон — 12 платных запросов и больше (починка JSON
добавляет запрос). Без настроенной модели команда завершается с кодом 2 и
подсказкой про `LLM_API_KEY`; ниже `--min-pass-rate` (по умолчанию 0,8) —
с кодом 1.

### Отчёт

`reports/evals/dialogues-<время>.json` хранит модель, хост API, число
пройденных сценариев и по каждому — провалы, ответ клиенту, решение о
допродаже и предупреждения. Папка в `.gitignore`.

Отчёт нужно **читать**, а не только смотреть на PASS. Пример с заглушкой
модели из [Testing](instructions/testing.md#manual-check-without-an-llm-key),
которая на любой вопрос отвечает одним и тем же текстом про покупку:

```text
PASS purchase-bedroom       Покупка с монтажом — допродажа уместна
FAIL unclear-price          Мало информации — уточняющий вопрос
     - upsell_applicable=True, ожидалось False
     - needs_clarification=False, ожидалось True
     - в ответе есть «42 900»
…
PASS unknown-product        Товара нет в базе: увлажнитель
…
Пройдено 3 из 12 (25%), порог 80%.
```

`unknown-product` прошёл, хотя ответ про кондиционер на вопрос об
увлажнителе бесполезен. Правила ловят известные ошибки — выдуманную цену,
неуместную допродажу, — но не любую плохую реплику. Поэтому в отчёте
сохраняется каждый ответ.

На настоящей модели набор ещё **не запускался**: во время разработки не
было ключа. Это первое, что стоит сделать, выбрав провайдера.

## 6. Вход менеджера: HTTP Basic

### Что закрыто

| Путь | Защита |
| --- | --- |
| `/`, `/static/*`, `/api/v1/suggest`, `/api/v1/knowledge-base`, `/docs`, `/openapi.json` | Логин и пароль менеджера, если заданы `UI_BASIC_AUTH_*` |
| `/api/v1/amocrm/suggest` | Одноразовый JWT виджета (этап 06) |
| `/api/v1/amocrm/webhook` | Секрет в URL (этап 06) |
| `/health` | Открыт: мониторинг и `HEALTHCHECK` в Docker |

### Почему HTTP Basic

Это встроенный в браузеры механизм: при ответе 401 с заголовком
`WWW-Authenticate: Basic` браузер сам показывает окно входа, а затем
отправляет заголовок `Authorization` со **всеми** запросами к тому же
адресу — и со страницей, и с `fetch()` из `app.js`. Интерфейс менять не
нужно. Для небольшой команды за HTTPS этого достаточно; отдельные учётные
записи менеджеров, роли или SSO потребуют хранилища пользователей.

Важно: Basic передаёт пароль в каждом запросе, закодированным base64, но не
зашифрованным. Без HTTPS его может прочитать любой на пути запроса.

### Как устроено

```python
class BasicAuthMiddleware:
    async def __call__(self, scope, receive, send):
        if scope["type"] != "http" or is_public_path(scope["path"]):
            await self.app(scope, receive, send)
            return
        ...
        if credentials_match(header, self._username, self._password):
            await self.app(scope, receive, send)
            return
        # 401 + WWW-Authenticate
```

- Это «чистое» ASGI-middleware: оно смотрит путь и заголовок до того, как
  запрос дойдёт до FastAPI, и не читает тело запроса.
- `credentials_match()` декодирует base64, делит строку по **первому**
  двоеточию (пароль может содержать «:») и сравнивает логин и пароль через
  `hmac.compare_digest` — за постоянное время, **обе** части всегда, чтобы
  время ответа не подсказывало верный логин.
- Логин и пароль задаются парой. Если задан один из них, `Settings`
  остановит запуск: «UI_BASIC_AUTH_USERNAME и UI_BASIC_AUTH_PASSWORD
  задаются вместе». Наполовину защищённый интерфейс хуже явной ошибки.
- Без `UI_BASIC_AUTH_*` сервер при запуске пишет в лог предупреждение, что
  интерфейс не защищён.
- В лог попадает только «basic auth rejected» — без логина, пароля и IP.

Фактический ответ без логина:

```text
HTTP/1.1 401 Unauthorized
www-authenticate: Basic realm="AI Sales Assistant", charset="UTF-8"
{"error":{"code":"unauthorized","message":"Введите логин и пароль менеджера."}}
```

## 7. Лимит генераций

Каждая генерация — платный запрос к модели. `RateLimiter` ограничивает
число генераций в минуту (`RATE_LIMIT_PER_MINUTE`, по умолчанию 30) на ключ:

| Эндпоинт | Ключ |
| --- | --- |
| `/api/v1/suggest` | IP клиента: `ip:<адрес>` |
| `/api/v1/amocrm/suggest` | Пользователь amoCRM из JWT: `amocrm:<account_id>:<user_id>` |

### Скользящее окно

Для каждого ключа хранится очередь времён последних запросов. При новом
запросе из очереди выбрасываются записи старше 60 секунд; если осталось
`limit` записей — ответ 429, иначе запрос учитывается:

```python
while calls and now - calls[0] >= self._window:
    calls.popleft()
if len(calls) >= self.limit:
    retry_after = max(1, int(self._window - (now - calls[0])) + 1)
    raise RateLimitedError(headers={"Retry-After": str(retry_after)})
calls.append(now)
```

В отличие от счётчика «на календарную минуту», скользящее окно не даёт
сделать двойной лимит на стыке минут.

- `Retry-After` — через сколько секунд освободится место. Для этого
  `AppError` научился передавать HTTP-заголовки.
- Ключей не больше 10 000: давно не встречавшиеся вытесняются (`OrderedDict`),
  память не растёт бесконечно.
- `RATE_LIMIT_PER_MINUTE=0` выключает лимит.
- Время берётся из `time.monotonic()` — его не сдвинет перевод часов. В
  тестах подставляются фальшивые часы, поэтому проверка окна мгновенная.

### За прокси

За обратным прокси (nginx, Caddy, балансировщик) все запросы приходят с
адреса прокси и делят один счётчик. Uvicorn берёт настоящий адрес из
`X-Forwarded-For`, только если запрос пришёл с адреса из переменной
окружения `FORWARDED_ALLOW_IPS` (по умолчанию `127.0.0.1,::1`), — укажите
там адрес прокси.

## 8. Как это проверено

- **Тесты:** 19 в `tests/test_access.py`, 10 в `tests/test_evals.py`, всего
  **124 passed**.
- **Оценка поиска:** hit@1 1.000, recall 1.000 на 24 вопросах; шаг добавлен
  в CI.
- **Оценка диалогов** прогнана на заглушке модели через настоящий
  HTTP-клиент: 3 из 12, код выхода 1, отчёт записан. На настоящей модели —
  не прогонялась.
- **Живой Uvicorn с curl:** без логина `/` → 401 с `WWW-Authenticate`;
  с логином → 200; неверный пароль на `/docs` → 401; `/health` → 200; при
  лимите 2 третья генерация → 429 с `retry-after: 59`. В логе нет пароля,
  заголовка `Authorization` и IP.
- **Браузер:** при лимите 1 первая генерация показала результат, вторая —
  плашку «Слишком много запросов. Подождите немного и попробуйте снова.».
- **Не проверено в браузере:** работа интерфейса за паролем — вход по ссылке
  с логином и паролем отклонён при проверке. На уровне HTTP поведение
  проверено curl и тестами.

## 9. Типичные ошибки

| Симптом | Причина | Что сделать |
| --- | --- | --- |
| Сервер не стартует: «…задаются вместе» | Задан только логин или только пароль | Задать оба или убрать оба |
| Браузер снова и снова просит пароль | Неверная пара или пробел в `.env` | Проверить значения; `curl -u` покажет 401/200 |
| Виджет amoCRM перестал работать после включения пароля | Не перестал: `/api/v1/amocrm/*` пароль не требует | Искать причину в JWT или CORS (этап 06) |
| Все менеджеры получают 429 одновременно | Сервис за прокси, все запросы с одного адреса | `FORWARDED_ALLOW_IPS=<адрес прокси>` или поднять `RATE_LIMIT_PER_MINUTE` |
| `run_evals.py retrieval` падает после правки базы | Новая позиция перетянула чужие вопросы | Посмотреть строку FAIL, дополнить `keywords` |
| `run_evals.py dialogues` завершается с кодом 2 | Нет модели в `.env` | Задать `LLM_API_KEY` или `LLM_BASE_URL` локальной модели |
| Сценарий проваливается на формулировке | В `reply_contains_any` стоит фраза, а не факт | Проверять факты: цены, сроки, ключевые слова |

## 10. Проверь себя

### Вопросы

1. Почему 124 зелёных теста не доказывают, что ассистент хорошо отвечает?
2. Чем hit@1 отличается от recall и зачем нужны обе метрики?
3. Почему оценка диалогов не запускается в CI?
4. Почему «Какой гарантийный срок?» находил график работы?
5. Зачем `credentials_match()` сравнивает логин и пароль всегда, даже если логин уже не совпал?
6. Почему лимит виджета считается по пользователю amoCRM, а не по IP?
7. Что увидит менеджер, если превысит лимит?

### Ответы

1. Ответ модели в тестах задаёт `FakeLLM`; тесты проверяют обработку ответа,
   а качество настоящей модели меряет оценка диалогов.
2. hit@1 — нужная позиция первая (важно для ответа), recall — обязательные
   позиции вообще попали в промпт (важно для допродажи).
3. Нужен ключ и каждый прогон платный; результат модели недетерминирован.
4. «Гарантия» встречается почти везде и весит мало, «срок» — редкое слово из
   ключевых слов графика. Исправлено ключевыми словами в базе знаний.
5. Чтобы время ответа не выдавало, что логин угадан.
6. Запросы из amoCRM идут из браузеров менеджеров, но пользователь в JWT
   точнее: один IP офиса может быть у многих менеджеров.
7. Плашку «Слишком много запросов. Подождите немного и попробуйте снова.»;
   API отвечает 429 с `Retry-After`.
