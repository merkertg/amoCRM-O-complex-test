# Восстановление после сбоев

[README](../README.md) · [Using the assistant](instructions/usage.md) ·
[Резервное копирование](instructions/backup.md) · [Версии и выпуск](RELEASES.md)

Сервис почти не хранит состояния: базы данных нет, ответы модели не
сохраняются. Поэтому большинство сбоев лечится перезапуском или исправлением
настроек, а потерять можно только две вещи, которые живут в памяти процесса:
кэш сообщений amoCRM и счётчики лимита генераций. Ниже — что происходит при
каждом типичном сбое, что увидит менеджер и как вернуть работу.

Коды ошибок и их тексты — в [Using the assistant](instructions/usage.md#status-codes-you-may-see).

## Перезапуск сервиса

**Что теряется.** Кэш сообщений из вебхуков amoCRM и счётчики лимита. Это
задумано: при чтении кэш отбирает сообщения не старше настроенного TTL
(по умолчанию 24 часа), а физическая очистка происходит при чтении или вытеснении
([Персональные данные](instructions/privacy.md)).

**Что увидит менеджер.** Виджет с пустым полем по старой сделке ответит
«В кэше нет сообщений клиента по этой сделке…» (`422 amocrm_no_message`).
Сервис не запрашивает историю доставленных вебхуков после перезапуска;
кэш наполняется следующими доставками.

**Что сделать.** Вставить текст сообщения клиента в поле виджета — ассистент
работает и без кэша. Новые сообщения снова попадут в кэш по вебхукам.

**Как проверить.**

```bash
curl -s http://127.0.0.1:8000/health
```

`"status":"ok"` — сервис поднялся, база знаний загружена.

## Сломанная правка базы знаний

**Симптом на работающем сервисе.** `/health` показывает `"status":"degraded"`
и `knowledge_base.last_error`. Ассистент продолжает отвечать по последней
корректной версии файла — менеджеры сбоя не замечают.

**Что сделать.** Исправить `data/knowledge_base.json` по тексту ошибки или
вернуть копию ([Резервное копирование](instructions/backup.md#восстановить-базу-знаний)).
Перезапуск не нужен: файл перечитывается при изменении.

**Симптом при запуске.** Если сломанный файл лежит на месте во время
перезапуска, сервис не стартует: `RuntimeError: База знаний не загружена: …`
в `docker compose logs assistant`, контейнер в статусе `unhealthy` или
перезапускается. Без корректного файла отвечать нечем — это намеренно.

**Как проверить.**

```bash
curl -s http://127.0.0.1:8000/health
.venv/bin/python scripts/run_evals.py retrieval
```

`"status":"ok"` и `Результат: PASS`: файл корректен и поиск не ухудшился.

## Модель недоступна

| Код | Что случилось | Что сделать |
| --- | --- | --- |
| `503 llm_unavailable` | Сеть, 429 или 5xx у провайдера; сервис уже сделал 3 попытки | Проверить статус провайдера и `LLM_BASE_URL`; повторить позже |
| `504 llm_timeout` | Модель не ответила за `LLM_TIMEOUT_SECONDS` | Повторить; при регулярных таймаутах увеличить таймаут или выбрать модель быстрее |
| `503 llm_auth` | Ключ отклонён (401/403) | Обновить `LLM_API_KEY` в `.env`, перезапустить: `docker compose up -d` |
| `502 llm_bad_request` | Модель или параметр не поддерживаются | Проверить `LLM_MODEL`; попробовать `LLM_TEMPERATURE=none`, `LLM_JSON_MODE=false` |

Ни один из этих сбоев не портит данные: запрос просто не выполнен.
Менеджер может ответить клиенту сам и повторить генерацию позже.

## REST API amoCRM недоступен или токен истёк

**Симптом.** Подсказка приходит, но с предупреждением «Не удалось загрузить
данные сделки из amoCRM — подсказка построена только по переписке»: нет имени
клиента. Строка `amocrm auth error: HTTP 401` в логе означает, что токен отклонён.

**Что сделать.** Срок [долгосрочного токена](https://www.amocrm.ru/developers/content/oauth/step-by-step)
выбирается при выдаче (от 1 дня до 5 лет): при истечении
сгенерировать новый в amoCRM (амоМаркет → интеграция → **Ключи** →
**Сгенерировать токен**), записать в `AMOCRM_ACCESS_TOKEN`, перезапустить.

## amoCRM отключил вебхук

**Почему.** По [документации amoCRM](https://www.amocrm.ru/developers/content/crm_platform/webhooks-format)
сервис ждёт ответ до 2 секунд; после более чем
100 невалидных откликов за 2 часа вебхук может отключиться, если последний
отклик на момент проверки также невалиден. Типичные причины: сервис
был недоступен или изменился `AMOCRM_WEBHOOK_SECRET` (ответ 403).

**Симптом.** Новые сообщения не попадают в кэш: виджет с пустым полем
отвечает `422 amocrm_no_message` даже по свежим диалогам.

**Что сделать.**

1. Убедиться, что сервис доступен снаружи по HTTPS, а секрет в URL вебхука
   совпадает с `AMOCRM_WEBHOOK_SECRET`.
2. В amoCRM: **амоМаркет** → **WEB HOOKS** → нажать **«Включить»** у вебхука
   и сохранить.
3. Отправить себе тестовое сообщение в подключённый чат и проверить, что в
   логе появилась строка `amocrm webhook received=1 stored=1`.

Сообщения за время отключения в кэш не попадут. Повторы доставки после сбоя
безопасны: сообщение с тем же `id` сохраняется один раз.

## Все менеджеры получают 429

**Причина.** Лимит считается по IP клиента. За обратным прокси или в Docker
все запросы приходят с одного адреса и делят один счётчик.

**Что сделать.** Указать адрес прокси в `FORWARDED_ALLOW_IPS`, чтобы Uvicorn
брал настоящий адрес из `X-Forwarded-For`, или поднять `RATE_LIMIT_PER_MINUTE`.
Подробно — [Access protection](instructions/access.md#rate-limit). Счётчики
обнуляются при перезапуске.

## Контейнер не становится healthy

```bash
docker compose ps
docker compose logs --tail 50 assistant
```

| В логе | Причина | Что сделать |
| --- | --- | --- |
| `База знаний не загружена` | Сломан или отсутствует `data/knowledge_base.json` | См. [сломанную правку](#сломанная-правка-базы-знаний) |
| `UI_BASIC_AUTH_USERNAME и UI_BASIC_AUTH_PASSWORD задаются вместе` | Задан только логин или только пароль | Задать оба или убрать оба |
| `validation error for Settings` | Неверный тип в `.env` (например, `LLM_TIMEOUT_SECONDS=быстро`) | Исправить значение по имени поля в сообщении |
| `env file .env not found` (от Compose) | Нет `.env` | `cp .env.example .env` |

## Если ничего не помогло

Соберите для разбора только технические данные: время, HTTP-статус, код ошибки из ответа
(`error.code`) и соответствующие строки лога. Для успешно созданной подсказки
доступен `meta.request_id`, который совпадает с `id` в логе `suggestion ready`.
Ответы с ошибкой такого идентификатора не содержат. Тексты
сообщений клиентов, имена, телефоны и ключи в отчёт об ошибке не вкладывайте —
в логах сервиса их нет по построению ([Персональные данные](instructions/privacy.md)).
