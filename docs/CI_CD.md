# CI/CD: проверки проекта и запуск контейнера

[README](../README.md) · [Короткая инструкция по CI](instructions/ci-and-delivery.md) ·
[Этап 07](STAGE_07.md) · [Демонстрация](DEMO.md)

Этот документ объясняет, что GitHub должен проверять после обновления
репозитория, как повторить проверки на своём компьютере и чем это отличается
от запуска приложения. Описание соответствует
[`.github/workflows/ci.yml`](../.github/workflows/ci.yml),
[`Dockerfile`](../Dockerfile) и [`docker-compose.yml`](../docker-compose.yml).

В проекте настроен **CI — автоматическая проверка изменений**. Сборка и
запуск Docker-контейнера выполняются вручную. Автоматическая публикация
образа в GHCR, выпуск релизов и развёртывание на сервере в workflow
не настроены.

Удалённый запуск GitHub Actions оставлен непроверенным по выбору
пользователя. Наличие workflow и успешные локальные команды не подтверждают
успех конкретного запуска на GitHub. Выполненные проверки и их ограничения
собраны в [отчёте](VERIFICATION.md); эта инструкция сама проверки не запускает.

## 1. Основные понятия

| Понятие | Значение для этого проекта |
| --- | --- |
| Commit | Сохранённая версия изменений в локальной истории Git. |
| Push | Отправка коммитов в репозиторий на GitHub. |
| Pull request, PR | Предложение включить изменения одной ветки в другую. |
| CI | Автоматическая проверка кода, тестов, поиска, ссылок и упаковки виджета. |
| CD | Доставка готового приложения или его развёртывание; в текущем workflow не реализована. |
| Workflow | Файл сценария GitHub Actions: `.github/workflows/ci.yml`. |
| Job | Задание workflow; здесь одно — `Python quality checks`. |
| Step | Шаг задания: например, установить зависимости или запустить pytest. |
| Runner | Машина, на которой GitHub выполняет задание. |
| Docker-образ | Упакованные приложение, Python и зависимости. |
| Контейнер | Запущенный экземпляр Docker-образа. |

Локальный `git commit` без `git push` не отправляет файлы на GitHub и
не вызывает удалённую проверку. Перед push полезно выполнить те же команды
локально, чтобы увидеть ошибку раньше.

## 2. Когда запускаются проверки

| Событие | Что предусмотрено workflow |
| --- | --- |
| Любой `push` в репозиторий | Запустить задание проверки; фильтра по веткам нет. |
| Создание или обновление PR | Запустить то же задание; фильтра по целевой ветке нет. |
| Ручной `workflow_dispatch` | Запустить то же задание для выбранной версии. |
| Только локальный commit | Удалённого запуска нет. |

Фильтра по изменённым путям тоже нет: обновление только документации
не исключено из проверок. Если ветка одновременно обновляет открытый PR,
события push и PR могут создать отдельные запуски.

Задание использует `ubuntu-latest`, Python 3.12 и общий тайм-аут **10 минут**.
Группа параллельности задана как `${{ github.workflow }}-${{ github.ref }}`:
новый запуск отменяет предыдущий для того же workflow и ref. Отменённый
запуск не считается успешной проверкой.

## 3. Что выполняется и в каком порядке

```text
push / pull_request / workflow_dispatch
                  |
                  v
checkout -> Python 3.12 -> pip install
                  |
                  v
Ruff -> mypy -> pytest -> retrieval -> documentation links -> widget.zip
```

GitHub сначала получает исходники и устанавливает зависимости из
[`requirements-dev.txt`](../requirements-dev.txt), который также включает
[`requirements.txt`](../requirements.txt). Для скачивания Actions и пакетов
нужен доступ к сети. Сами тесты подменяют модель объектом `FakeLLM`, а HTTP
провайдера и amoCRM — `httpx.MockTransport`: ключи и настоящий аккаунт
для этих проверок не нужны.

После установки зависимостей идут шесть проверок:

| Шаг | Команда из workflow | Что проверяет |
| --- | --- | --- |
| Ruff | `python -m ruff check app tests scripts evals` | Выбранные правила ошибок кода, синтаксиса и порядка импортов; форматирование не является отдельным барьером CI. |
| mypy | `python -m mypy app evals` | Типы в приложении и модуле оценок; тесты и генератор PDF в эту область не входят. |
| pytest | `python -m pytest` | Автотесты сервиса без сети; текущая документированная база — 124 теста. |
| Retrieval | `python scripts/run_evals.py retrieval` | Поиск по 24 вымышленным вопросам и заданные пороги качества. |
| Ссылки | `python scripts/check_docs.py` | Локальные ссылки и Markdown-якоря в README, AGENTS и документации. |
| Виджет | `python scripts/build_widget.py` | Обязательные файлы, JSON манифеста и локализаций; затем создание `dist/widget.zip`. |

Шаги выполняются последовательно: ошибка останавливает обычное выполнение
следующих проверок. Например, при провале mypy нельзя считать pytest
успешным в этом запуске — он ещё не выполнялся.

Упаковка виджета не устанавливает его в amoCRM. Workflow не сохраняет архив
отдельным скачиваемым артефактом Actions и не публикует его: `dist/widget.zip`
создаётся в рабочем каталоге runner. Для загрузки виджета вручную смотри
[инструкцию amoCRM](instructions/amocrm.md).

### Пороги поиска

В [`evals/retrieval.json`](../evals/retrieval.json) установлены:

- `min_hit_at_1 = 0.95` — доля вопросов, где ожидаемая позиция найдена первой;
- `min_recall = 1.0` — средняя доля обязательных позиций, попавших в результат.

Если качество ниже порога, команда возвращает код ошибки и CI останавливается.
После изменения базы знаний или поиска запускай эту оценку отдельно.
При провале анализируй найденные позиции и дополняй `keywords` в
[`data/knowledge_base.json`](../data/knowledge_base.json), сохраняя пороги.
Подробное объяснение метрик и разницы между оценкой поиска и оценкой настоящей
модели — в [этапе 08](STAGE_08.md) и
[короткой инструкции](instructions/evaluations.md).

### Настройки доступа workflow

У workflow только разрешение `contents: read`. Checkout не сохраняет
учётные данные GitHub в локальной конфигурации Git
(`persist-credentials: false`). `actions/checkout` и `actions/setup-python`
закреплены полными SHA коммитов; комментарии рядом указывают версии v7.
В workflow нет обращения к ключу LLM или токену amoCRM.

Эти настройки описывают полномочия задания GitHub. Доступ менеджера к
запущенному приложению регулируется отдельно — смотри
[защиту доступа](instructions/access.md).

## 4. Как повторить проверки локально

Выполни из корня проекта. Создание окружения нужно только при его отсутствии;
установка зависимостей может обращаться к сети.

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m ruff check app tests scripts evals
.venv/bin/python -m mypy app evals
.venv/bin/python -m pytest
.venv/bin/python scripts/run_evals.py retrieval
.venv/bin/python scripts/check_docs.py
.venv/bin/python scripts/build_widget.py
```

Это те же области проверки, что и в CI. Они не включают запуск настоящей
LLM, проверку реального аккаунта amoCRM, браузерный показ, сборку контейнера
и визуальный просмотр PDF. Для них есть отдельные процедуры в
[инструкции проверки](instructions/testing.md),
[сценарии демонстрации](DEMO.md) и
[инструкции пересборки PDF](guide/README.md).

## 5. Как прочитать результат на GitHub

Открой [Actions репозитория](https://github.com/merkertg/amoCRM-O-complex-test/actions),
выбери workflow **CI**, затем запуск для нужного commit и задания
**Python quality checks**. Проверь SHA коммита, итог задания и результаты
всех шести шагов после установки зависимостей.

| Результат | Как понимать |
| --- | --- |
| Успешно | Проверки этого запуска прошли для указанного коммита. |
| Ошибка | Открой первый упавший шаг; последующие могли не выполняться. |
| Отменён | Найди более новый запуск для того же ref и проверь его отдельно. |
| Нет доступа или запуск не просмотрен | Удалённый результат остаётся непроверенным. |

Сейчас удалённый CI оставлен непроверенным по выбору пользователя.
Не заменяй этот статус выводом локальной команды. Если позднее удалённый
запуск будет проверен, зафиксируй commit, результат и источник подтверждения
в [VERIFICATION.md](VERIFICATION.md).

## 6. Как связан Docker

[`Dockerfile`](../Dockerfile) описывает образ на `python:3.12-slim`:
runtime-зависимости из `requirements.txt`, код `app/`, база знаний `data/`,
запуск Uvicorn и проверка `/health`. Процесс работает от пользователя
`appuser` с UID 10001. Uvicorn запускается одним процессом: кэш сообщений
amoCRM и счётчики ограничения генераций хранятся в его памяти и сбрасываются
после перезапуска. Несколько реплик не получают общий кэш автоматически.

В [`docker-compose.yml`](../docker-compose.yml) один сервис `assistant`.
Он собирает локальный образ `amocrm-sales-assistant:latest`, читает настройки
из `.env`, публикует порт 8000 и монтирует `./data` в `/app/data` только
для чтения. Изменение локальной базы знаний поэтому доступно приложению
без пересборки образа.

После подготовки настроек по [Quickstart](instructions/quickstart.md)
стенд запускается вручную:

```bash
docker compose up --build
```

Compose публикует порт без ограничения адресом `127.0.0.1`. Если интерфейс
доступен за пределами localhost, заранее задай оба параметра
`UI_BASIC_AUTH_*` и используй HTTPS по
[инструкции защиты доступа](instructions/access.md). Значения секретов
не попадают в Git и документацию.

Команда запуска контейнера не входит в текущее задание CI. Само наличие
Dockerfile или успешные Python-тесты не подтверждают сборку и запуск образа;
фактические результаты ручных проверок записываются отдельно. Создание
локального тега `latest` также не публикует образ в реестр.

## 7. Что делать при ошибке

| Первый упавший шаг | Следующее действие |
| --- | --- |
| Установка зависимостей | Проверь Python 3.12 и первую ошибку pip; остальные проверки ещё не начались. |
| Ruff | Прочитай файл, строку и код правила; исправь причину и повтори команду. |
| mypy | Проверь ожидаемый тип и фактическое значение; уточни аннотацию или обработай `None`. |
| pytest | Повтори проблемный тест; сохраняй `FakeLLM` и `MockTransport` вместо сетевых вызовов. |
| Retrieval | Сопоставь ожидаемую и найденную позиции, дополни ключевые слова базы и повтори оценку без снижения порогов. |
| Ссылки | Исправь относительный путь или якорь, указанный `check_docs.py`. |
| Виджет | Восстанови обязательный файл или корректный JSON; затем повтори упаковку. |

После исправления обнови затронутую инструкцию, [журнал](DEVELOPMENT_LOG.md)
и [отчёт проверок](VERIFICATION.md). При изменении учебного материала или
подтверждённых результатов также обнови сводку и обе версии PDF по
[инструкции руководства](guide/README.md).
