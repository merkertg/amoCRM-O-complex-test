# Этап 07. CI и качество кода: подробное руководство

На этом этапе проверки проекта запускаются одинаковыми командами локально
и в GitHub Actions. Это продолжение шести этапов исходного ТЗ: приложение
уже умеет готовить два блока ответа, а теперь изменения автоматически
проверяются перед дальнейшей работой.

Короткая английская инструкция — [CI and code quality](instructions/ci.md).
Предыдущий этап — [интеграция с amoCRM](STAGE_06.md), устройство тестов —
[этап 05](STAGE_05.md). Фактические результаты записываются в
[отчёт о проверке](VERIFICATION.md).

## 1. Что появилось

| Файл | Что в нём |
| --- | --- |
| [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) | События запуска, Linux-окружение, Python и последовательность проверок |
| [`requirements-dev.txt`](../requirements-dev.txt) | pytest, Ruff 0.17.1 и mypy 2.4.0; также подключены зависимости приложения |
| [`pyproject.toml`](../pyproject.toml) | Правила Ruff, параметры mypy и существующие настройки pytest |
| [`scripts/check_docs.py`](../scripts/check_docs.py) | Проверка локальных ссылок и якорей Markdown без сети |
| [`scripts/build_widget.py`](../scripts/build_widget.py) | Проверка файлов виджета и сборка `dist/widget.zip` |

Все проверки обходятся без ключа LLM, токена amoCRM и настоящей переписки.
Скачивание зависимостей при подготовке окружения использует сеть; сами
тесты работают с подменёнными моделью и HTTP.

## 2. Что означает CI

CI — Continuous Integration, непрерывная интеграция. В этом проекте это
набор команд, который GitHub запускает после изменения репозитория.

Например, разработчик меняет `app/core/assistant.py` и отправляет коммит.
GitHub создаёт отдельное окружение, загружает код и последовательно
проверяет его. Если mypy находит обращение к атрибуту у значения, которое
может быть `None`, этап проверки типов завершается ошибкой. До тестов этот
запуск уже не дойдёт.

Так ошибка становится видна рядом с конкретным коммитом. Чтобы понять
причину, нужно открыть упавший шаг и прочитать сообщение с именем файла и
номером строки.

Настройка CI сама по себе не вводит запрет на слияние изменений. Правила
защиты ветки и обязательные проверки настраиваются отдельно в GitHub.

## 3. Как повторить проверки локально

Выполняй команды из корня проекта — папки, где лежат `app`, `tests` и
`requirements-dev.txt`. Для нового окружения:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

Если `.venv` уже создан на Python 3.12, заново создавать его не нужно:
достаточно установить обновлённые зависимости. Проверить версию можно
командой `.venv/bin/python --version`.

Затем выполни те же проверки, что и workflow:

```bash
.venv/bin/python -m ruff check app tests scripts
.venv/bin/python -m mypy app
.venv/bin/python -m pytest
.venv/bin/python scripts/check_docs.py
.venv/bin/python scripts/build_widget.py
```

Здесь указан путь `.venv/bin/python`, поэтому не нужно отдельно
активировать окружение. Все инструменты запускаются через один Python.

Успешные проверки Ruff и mypy возвращают код завершения `0`; pytest должен
показать `95 passed` для текущего набора сервисных тестов. Время выполнения
может отличаться. Проверка документации печатает число просмотренных файлов
и ссылок, а также число ошибок: ожидается `0 broken links`. Сборщик виджета
сообщает о создании `dist/widget.zip`.

Это ожидаемые признаки успеха, а результат конкретного прогона нужно
смотреть в терминале и записывать в [VERIFICATION.md](VERIFICATION.md).

## 4. Ruff: ошибки в коде и порядок импортов

Ruff быстро анализирует исходный код. В проекте включены пять групп правил:

| Группа | Что ищет |
| --- | --- |
| `E4` | Ошибки, связанные с импортами |
| `E7` | Некоторые ошибочные конструкции и сравнения |
| `E9` | Ошибки разбора и другие серьёзные ошибки кода |
| `F` | Например, неиспользуемые импорты и неизвестные имена |
| `I` | Порядок импортов |

Область проверки — `app`, `tests` и `scripts`, в том числе исходники
PDF-руководства. Команда `ruff check` не запускает форматирование. В CI
нет отдельного шага `ruff format --check`, а длина строки не включена в
выбранные правила как отдельное требование.

Допустим, Ruff сообщает `I001` в начале файла: блок импортов расположен
не в ожидаемом порядке. Можно поправить его вручную или запустить:

```bash
.venv/bin/python -m ruff check app tests scripts --fix
git diff
```

`--fix` меняет файлы. После него прочитай изменения и повтори проверки.
Обычный шаг CI использует команду без `--fix`: он показывает ошибку и не
исправляет репозиторий сам.

## 5. mypy: согласованность типов приложения

mypy проверяет, как значения передаются между функциями. Сейчас область
проверки — все **27 Python-модулей в `app`**, включая `__init__.py`.
Тесты и скрипты PDF не включены в эту проверку типов.

Основные параметры в `pyproject.toml`:

```toml
[tool.mypy]
python_version = "3.12"
files = ["app"]
check_untyped_defs = true
disallow_untyped_defs = true
warn_unused_ignores = true
warn_redundant_casts = true
strict_equality = true
enable_error_code = ["ignore-without-code"]
```

`disallow_untyped_defs` требует аннотации у определений функций;
`check_untyped_defs` также включает проверку тел функций без аннотаций,
если такие встретятся. Остальные параметры помогают замечать устаревшие
подавления ошибок, лишние приведения и некоторые бессмысленные сравнения.
Это явно выбранный набор проверок, а не режим `strict = true`.

Пример типичной проблемы:

```python
def normalise_name(name: str | None) -> str:
    return name.strip()
```

`name` может оказаться `None`, у которого нет метода `strip`. Нужно
решить, что функция делает без имени, и отразить это в коде:

```python
def normalise_name(name: str | None) -> str:
    if name is None:
        return ""
    return name.strip()
```

В этих учебных примерах `normalise_name` — условная функция, а не новый
модуль проекта. Типы помогают найти противоречие в программе, но не
проверяют, правильно ли LLM ответила на вопрос клиента или указала цену.

Не скрывай проблему общим `# type: ignore`. Сначала уточни тип или условие
проверки. Если подавление необходимо, оно должно иметь конкретный код
ошибки; `ignore-without-code` не допускает подавление без такого кода.

## 6. pytest: поведение сервиса без внешних сервисов

Существующие 95 тестов остаются проверкой поведения. Ruff может не найти
ошибок, а mypy — подтвердить типы, но это ещё не доказывает, что неизвестная
допродажа заблокирована или телефон скрыт перед передачей в модель.

В тестах LLM заменена на `FakeLLM`, обращения HTTP — на
`httpx.MockTransport`. `TestClient` вызывает приложение напрямую, без
Uvicorn и сетевого порта. Настройки тестов не читают рабочий `.env`.

Не добавляй в CI настоящие ключи ради этих тестов. Новый тест LLM должен
задавать ответ через `FakeLLM`, а тест HTTP-клиента — формировать ответ
через `MockTransport`, как описано на [этапе 05](STAGE_05.md).

Для разбора одного сбоя:

```bash
.venv/bin/python -m pytest tests/test_assistant.py -v
.venv/bin/python -m pytest -k injection -v
```

## 7. Документация и архив виджета

`check_docs.py` читает `README.md`, `AGENTS.md` и Markdown-файлы в `docs`.
Он проверяет, существует ли локальный путь из ссылки, а у ссылки на
заголовок — существует ли нужный якорь. Для этого не нужен интернет.
Внешние URL не открываются, поэтому успешный запуск не подтверждает
доступность сайта amoCRM или GitHub.

Например, после переименования заголовка ссылка на старый якорь может
сломаться. Скрипт укажет Markdown-файл, строку и причину `missing anchor`.
Исправь ссылку или заголовок и запусти проверку ещё раз.

`build_widget.py` проверяет обязательные файлы и JSON, включая локализации
из манифеста, после чего создаёт `dist/widget.zip`. Архив находится в
игнорируемой папке `dist`: шаг не загружает его в amoCRM. В workflow нет
шага публикации архива как отдельного GitHub artifact.

Сборка и визуальная проверка PDF выполняются отдельно по
[инструкции](guide/README.md). CI не устанавливает `requirements-guide.txt`
и не рендерит страницы. Если изменился учебный материал, обязательная
пересборка обеих версий PDF и их визуальная проверка сохраняются.

## 8. Как устроен workflow

| Настройка | Что происходит |
| --- | --- |
| `push` | Проверки запускаются после отправки коммитов в любую ветку |
| `pull_request` | Проверки запускаются для событий pull request; фильтра веток нет |
| `workflow_dispatch` | Доступен ручной запуск из GitHub Actions |
| `ubuntu-latest` | Задание выполняется на Linux-машине GitHub |
| Python `3.12` | Используется нужная ветка версии Python |
| `timeout-minutes: 10` | Зависшее задание не работает бесконечно |
| `contents: read` | Встроенный токен workflow имеет право читать содержимое репозитория |
| `persist-credentials: false` | Checkout не сохраняет Git-учётные данные для дальнейших шагов |
| `cancel-in-progress: true` | Новый запуск для той же группы отменяет старый |

Группа параллельных запусков содержит имя workflow и `github.ref`.
Поэтому новый коммит в той же ветке отменяет устаревший прогон этой
группы, а проверки другой ветки продолжают работать. Отменённый запуск
не считается успешной проверкой: смотри новый прогон.

В workflow один job. Он получает код через `actions/checkout`, настраивает
Python через `actions/setup-python`, скачивает зависимости и выполняет
пять проверок по порядку. Для действий указаны полные SHA коммитов, а
комментарии помечают версию v7. При обновлении действия нужно проверять
новую версию и менять SHA осознанно; одного изменения комментария мало.

Workflow не обращается к application secrets и не требует настройки
`LLM_API_KEY`, токена amoCRM или секретов интеграции. Стандартный токен
GitHub для чтения репозитория не является токеном приложения.

## 9. Как проверить запуск на GitHub

1. Отправь изменения в нужную ветку репозитория.
2. Открой [Actions](https://github.com/merkertg/amoCRM-O-complex-test/actions).
3. Найди workflow **CI** и запуск для нужного коммита или pull request.
4. Открой job **Python quality checks** и проверь результат каждого шага.
5. Если есть ошибка, исправь её локально, повтори команды и отправь новый
   коммит. Зафиксируй итог в [VERIFICATION.md](VERIFICATION.md).

Файл workflow и успешные локальные команды — это ещё не результат
удалённого запуска. Утверждать, что CI прошёл на GitHub, можно после
проверки конкретного run. До этого удалённый CI нужно указывать как
непроверенный. В этом руководстве успешный run не объявляется заранее.

## 10. Типичные ошибки

| Симптом | Что проверить |
| --- | --- |
| `No module named ruff` или `mypy` | Установлены ли обновлённые `requirements-dev.txt` в том же `.venv` |
| pip не смог установить пакет | Python 3.12, доступ к индексу пакетов и первая ошибка pip; последующие проверки ещё не выполнены |
| Ruff сообщает `I001` | Порядок импортов в указанном файле |
| mypy сообщает об `Optional` или `None` | Проверяется ли отсутствие значения до обращения к методу или атрибуту |
| mypy требует аннотацию функции | Указаны ли типы аргументов и возвращаемого значения, включая `-> None` |
| Тест пытается вызвать настоящую модель | Использованы ли `FakeLLM` и тестовые настройки вместо рабочего окружения |
| `missing file` или `missing anchor` | Относительный путь ссылки и действительный заголовок Markdown |
| Сборщик виджета не находит файл | Состав `amocrm_widget` и локализации из `manifest.json` |
| В GitHub после ошибки остальные шаги серые | Job останавливает последовательность после неуспешного шага; сначала исправь его |
| Старый run помечен `Cancelled` | Появился ли новый запуск для того же ref; оцени результат нового |

## 11. Проверь себя

### Вопросы

1. Почему Ruff, mypy и pytest нужны одновременно?
2. Почему тестам не нужен ключ LLM, хотя установка зависимостей использует сеть?
3. Что именно доказывает успешный `check_docs.py`?
4. Можно ли назвать виджет проверенным в amoCRM после создания ZIP?
5. Чем локальный успешный прогон отличается от успешного CI run?
6. Почему пересборку PDF нельзя заменить прохождением этого workflow?

### Ответы

1. Ruff проверяет выбранные ошибки исходного кода и импорты, mypy —
   согласованность типов, pytest — поведение на заданных сценариях.
2. Зависимости скачиваются до тестов. Внутри тестов используются заранее
   заданные ответы `FakeLLM` и `MockTransport`, поэтому внешние сервисы не нужны.
3. Существуют проверяемые локальные пути и якоря Markdown. Скрипт не
   открывает внешние URL и не оценивает правильность текста.
4. Нет. Создание ZIP подтверждает проверенные файлы и упаковку; загрузка
   и работа в настоящем аккаунте требуют отдельного прогона.
5. Локально проверен компьютер разработчика. CI run выполняет команды
   на GitHub для конкретного коммита и имеет собственный результат.
6. Workflow не собирает и не рендерит PDF. Ошибки вёрстки нужно искать
   после пересборки обеих языковых версий и просмотра всех страниц.

## 12. Что остаётся за границей этапа

Этот этап не доказывает качество ответов настоящей LLM, работу виджета в
реальном amoCRM, браузерную вёрстку или запуск Docker-контейнера.
Требование к ассистенту сохраняется: клиенту отправляет сообщение только
менеджер. Следующие изменения — например, Redis для нескольких реплик —
должны иметь свои проверки и обновлённую документацию.
