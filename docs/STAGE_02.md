# Этап 02. База знаний и поиск: подробное руководство

Этот документ объясняет, где ассистент берёт факты о товарах, ценах и
условиях, как эти факты проверяются, как база знаний обновляется без
перезапуска сервера и как из неё выбираются фрагменты, которые увидит
модель. Команды выполняются из папки `amoCRM` с активированным `.venv`.

## 1. Что получилось на этом этапе

| Что | Где | Зачем |
| --- | --- | --- |
| Демонстрационная база | `data/knowledge_base.json` | 10 товаров и услуг, 7 общих условий вымышленной компании КлиматДом |
| Схема базы | `app/knowledge/models.py` | Проверяет каждое поле, уникальность `id` и ссылки `related` |
| Загрузка | `app/knowledge/repository.py` | Читает файл, перечитывает при изменении, переживает сломанную правку |
| Поиск | `app/knowledge/search.py` | Находит позиции, которые относятся к вопросу клиента |
| Отображение для модели | `app/core/prompts.py` | Превращает позицию в компактный текстовый блок фактов |
| 19 тестов | `tests/test_knowledge_base.py` | Валидация, перезагрузка, стемминг, ранжирование |

ТЗ требует, чтобы базу знаний можно было **редактировать без изменения
Python-кода**, и чтобы LLM **использовала только предоставленные факты**.
Первое даёт JSON-файл с автоматической перезагрузкой, второе — правила
промпта и серверные проверки (этап 03), которые опираются на эту же базу.

## 3. Формат файла

Верхний уровень — три раздела:

```json
{
  "company": {"name": "КлиматДом", "description": "...", "working_hours": "Ежедневно с 9:00 до 21:00"},
  "products": [ ... ],
  "faq": [ ... ]
}
```

Одна позиция (сокращённо, полностью — в файле):

```json
{
  "id": "breeze-09",
  "type": "product",
  "name": "Сплит-система «Бриз 09»",
  "category": "Кондиционеры",
  "description": "Инверторная настенная сплит-система для помещений до 25 м²...",
  "features": ["Площадь помещения: до 25 м²", "Мощность охлаждения: 2,6 кВт", "..."],
  "price": {"amount": 42900, "unit": "за комплект (внутренний и наружный блок)"},
  "terms": ["Гарантия на оборудование — 3 года ...", "Доставка по Москве бесплатно", "Монтаж оплачивается отдельно"],
  "related": ["install-standard", "wifi-module", "service-plan", "extended-warranty"],
  "upsell_scenarios": ["Клиент покупает кондиционер, но не говорил про установку — предложить стандартный монтаж ..."],
  "keywords": ["кондиционер", "сплит", "спальня", "детская", "кондей", "кондер"]
}
```

Каждое поле из ТЗ есть в схеме:

| Требование ТЗ | Поле |
| --- | --- |
| Название | `name` |
| Описание | `description` |
| Основные характеристики | `features` |
| Стоимость, если известна | `price.amount` (или `null`, если цена не фиксирована) |
| Условия предоставления | `terms` |
| Связанные товары и услуги | `related` |
| Возможные сценарии допродажи | `upsell_scenarios` |

Дополнительно: `id` — короткий латинский код, по нему сервер проверяет
рекомендацию модели; `type` — товар или услуга; `category`; `keywords` —
синонимы и разговорные слова для поиска.

`faq` — общие условия, которые не привязаны к одному товару: доставка,
оплата, гарантия, зона обслуживания, сроки, ремонт, возврат.

### Цена, которая неизвестна

У позиции «Демонтаж старого кондиционера» цена зависит от этажа и доступа:

```json
"price": {"amount": null, "note": "стоимость рассчитывает мастер после осмотра: ..."}
```

`Price.render()` в таком случае возвращает текст из `note`, а не число.
Модель видит «цена: стоимость рассчитывает мастер после осмотра» и не
может её выдумать — это частый источник ошибок у LLM, поэтому такой пример
специально есть в демо-базе.

## 4. Проверка файла: app/knowledge/models.py

Файл — это данные, которые правит человек, поэтому каждое поле проверяется
Pydantic-моделями при загрузке.

```python
class KnowledgeBase(BaseModel):
    company: Company
    products: list[Product]
    faq: list[FAQEntry] = Field(default_factory=list)

    @model_validator(mode="after")
    def _check_ids(self) -> "KnowledgeBase":
        ids = [p.id for p in self.products] + [f.id for f in self.faq]
        duplicates = {i for i in ids if ids.count(i) > 1}
        if duplicates:
            raise ValueError(f"Повторяющиеся id: {sorted(duplicates)}")
        product_ids = {p.id for p in self.products}
        for product in self.products:
            unknown = set(product.related) - product_ids
            if unknown:
                raise ValueError(f"{product.id}: неизвестные id в related: {sorted(unknown)}")
        return self
```

Что ловится до того, как ошибка дойдёт до клиента:

| Ошибка в файле | Что скажет проверка |
| --- | --- |
| Нет `name` или `description` | `Field required` с путём `products.3.name` |
| `"type": "товар"` | `Input should be 'product' or 'service'` |
| `"id": "Монтаж"` | `String should match pattern '^[a-z0-9][a-z0-9\-]*$'` |
| Два одинаковых `id` | `Повторяющиеся id: ['a']` |
| `related` ссылается на несуществующую позицию | `breeze-09: неизвестные id в related: ['zzz']` |
| Отрицательная цена | `Input should be greater than or equal to 0` |

Тексты в таблице — фактические сообщения проверки.

`KnowledgeBase` также даёт удобные методы: `get_product(id)`,
`get_faq(id)` и `find_product_by_name(name)`. Последний нужен на этапе 03:
если модель назвала товар, но забыла `id`, сервер найдёт позицию по
названию — только при точном или однозначном совпадении.

## 5. Загрузка и перезагрузка без перезапуска

```python
def get(self) -> KnowledgeBase:
    with self._lock:
        mtime = self._current_mtime()
        if self._kb is None or (mtime is not None and mtime != self._mtime):
            self._load(mtime)
        if self._kb is None:
            raise KnowledgeBaseError()
        return self._kb
```

Как это работает:

1. При каждом запросе ассистент вызывает `repo.get()`.
2. `get()` сравнивает время изменения файла (`mtime`) с запомненным. Это
   один системный вызов `stat()` — дешевле, чем читать файл.
3. Если файл изменился — читает его заново и проверяет моделью.
4. Если новая версия **невалидна**, в `_load()` срабатывает `except`:
   ошибка запоминается в `last_error`, а `self._kb` остаётся прежним.
   Сервис продолжает отвечать по последней корректной версии.
5. `mtime` сломанного файла тоже запоминается, чтобы не перечитывать его
   на каждом запросе.
6. `threading.Lock` защищает от одновременной перезагрузки из двух потоков.

При **запуске** всё строже: `create_app()` вызывает `repo.get()` и, если
корректной версии нет совсем, останавливает запуск.

### Эксперимент: правка на лету

В одной вкладке запусти сервер, в другой:

```bash
curl -s http://127.0.0.1:8000/api/v1/knowledge-base | python -m json.tool | grep -A1 '"wifi-module"'
```

Поменяй в `data/knowledge_base.json` цену Wi-Fi модуля с `3500` на `3900`,
сохрани и повтори запрос — цена изменится без перезапуска. Теперь удали
одну закрывающую скобку и сохрани:

```bash
curl -s http://127.0.0.1:8000/health
```

`"status": "degraded"`, в `knowledge_base.last_error` — тип и место
ошибки JSON. Ассистент при этом продолжает работать по версии с ценой 3900.
Верни скобку — статус снова `ok`.

Тот же сценарий автоматически проверяют тесты
`test_knowledge_base_reloads_after_edit` и
`test_broken_edit_keeps_last_valid_version`.

### В Docker

`docker-compose.yml` монтирует папку `./data` в контейнер только для чтения
(`./data:/app/data:ro`). Правка файла на компьютере сразу видна внутри
контейнера, пересобирать образ не нужно.

## 6. Как факт выглядит для модели

Модель получает не JSON, а компактный текст — так меньше токенов и проще
читать. `render_product()` в `app/core/prompts.py` для «Бриз 09» выдаёт
(фактический вывод):

```text
[breeze-09] Сплит-система «Бриз 09» — товар, категория «Кондиционеры»
Описание: Инверторная настенная сплит-система для помещений до 25 м²: спальня, детская, небольшой кабинет.
Характеристики: Площадь помещения: до 25 м²; Мощность охлаждения: 2,6 кВт; ...
Цена: 42 900 ₽ за комплект (внутренний и наружный блок)
Условия: Гарантия на оборудование — 3 года при установке сертифицированными мастерами; Доставка по Москве бесплатно; Монтаж оплачивается отдельно
Связанные позиции: [install-standard] Стандартный монтаж сплит-системы; [wifi-module] Wi-Fi модуль «Бриз Коннект»; ...
Сценарии допродажи (только для менеджера): Клиент покупает кондиционер, но не говорил про установку — ...
```

`[breeze-09]` в начале — это `id`. Модель должна вернуть его в
`upsell_product_id`, а сервер сверит его с базой.

## 7. Поиск: токены и основы слов

Векторная база данных для двух десятков записей избыточна (ТЗ прямо об этом
говорит). Поиск по ключевым словам прозрачен: всегда можно объяснить,
почему найдена именно эта позиция.

Проблема русского языка — падежи: «установка», «установку», «установить».
Простое сравнение слов их не свяжет. Поэтому каждое слово проходит через
`tokenize()`:

1. Нижний регистр, `ё → е`.
2. Слова длиной от 2 символов, кроме стоп-слов («сколько», «стоит»,
   «здравствуйте», «пожалуйста» и т. п. — они есть почти в каждом вопросе
   и ничего не говорят о товаре).
3. `stem()` отрезает одно типичное окончание (самое длинное подходящее) и
   оставляет основу до 6 букв. Основа не может стать короче 3 букв.

Фактические результаты:

| Слово | Основа |
| --- | --- |
| установку, установка, установить | `устано` |
| кондиционера | `кондиц` |
| гарантийный | `гарант` |
| чистку | `чистк` |

### Слово + число

«Бриз 18» — это модель, а «18 м²» — площадь. Если считать «18» отдельным
словом, вопрос «кондиционер в спальню 18 м²» найдёт «Бриз 18», рассчитанный
на 50 м². Поэтому число, стоящее сразу после слова, склеивается с ним:

```text
tokenize("Сколько стоит установка Бриз 09 в спальню 18 м²?")
→ ['устано', 'бриз', 'спальн', 'бриз#09', 'спальн#18']
```

Токен `бриз#09` есть только у «Бриз 09», а `спальн#18` не совпадает ни с
чем. Эта ошибка была найдена при ручной проверке и исправлена — подробности
в [отчёте о проверке](VERIFICATION.md).

## 8. Поиск: оценка релевантности

`KnowledgeIndex` один раз строит для каждой позиции наборы токенов по
полям и считает IDF — «редкость» токена:

```text
IDF(токен) = ln(1 + N / df)
N  — число документов (10 позиций + 7 FAQ = 17)
df — в скольких документах встречается токен
```

Чем реже слово, тем больше оно говорит о вопросе. Оценка документа:

```text
score = Σ по токенам запроса: вес лучшего поля × IDF × вес запроса
```

| Поле | Вес |
| --- | --- |
| `name`, `keywords`, `topic` (FAQ) | 3 |
| `category` | 2 |
| `description`, `features`, `terms`, `answer` | 1 |

Вес запроса: токены текущего сообщения — 1.0, токены последних трёх
сообщений клиента из истории — 0.5.

### Разобранный пример: «Сколько стоит монтаж?»

После `tokenize()` остаётся один токен — `монтаж` («сколько» и «стоит» —
стоп-слова). Он встречается в 11 документах из 17:

```text
IDF(монтаж) = ln(1 + 17 / 11) = 0.934
```

- «Стандартный монтаж сплит-системы»: `монтаж` в названии (вес 3) →
  3 × 0.934 = **2.803**;
- «Бриз 09/12/18», «Демонтаж…», Wi-Fi модуль и ещё шесть позиций:
  `монтаж` только в условиях (вес 1) → **0.934**.

Монтаж уверенно на первом месте. В промпт уходят первые `KB_TOP_K = 5`
совпадений и до трёх связанных позиций.

### Разобранный пример: контекст истории

Клиент сначала написал «Присматриваюсь к Бриз 12», а теперь спрашивает
«А сколько стоит?». В текущем сообщении после стоп-слов не осталось ничего,
но токены истории идут с весом 0.5:

```text
search("А сколько стоит?", context="Присматриваюсь к Бриз 12")
→ breeze-12 (6.351), breeze-09 (2.016), breeze-18 (2.016), wifi-module (2.016), ...
```

`бриз#12` есть только у «Бриз 12», поэтому он первый.

## 9. Связанные позиции и каталог

После ранжирования `_related()` добавляет до трёх позиций из `related`
найденных товаров с пометкой `reason="related"`. Это кандидаты для
допродажи: если клиент спрашивает про кондиционер, модель должна видеть
полные факты о монтаже и Wi-Fi модуле, чтобы рекомендовать их с ценой
из базы.

В промпте такие позиции подписаны «(связанная позиция)». Кроме того,
модель получает **каталог** — список всех названий без цен (`<catalog>`).
Он нужен для уточняющих вопросов: «Вас интересует кондиционер, монтаж или
обслуживание?» — но называть цены по каталогу правила запрещают.

Если по вопросу не нашлось ничего («Добрый день!»), в промпт уходит
«Релевантных фактов не найдено», а менеджер получает предупреждение.

## 10. Как улучшить поиск

Поиск не понимает смысла: слова, которых нет в базе, он не найдёт. Если
вопрос попадает не туда:

1. Задай вопрос в интерфейсе и открой «Источники и технические детали» —
   там список позиций, которые получила модель.
2. Добавь разговорные слова и синонимы в `keywords` нужной позиции
   («кондей», «сплит», «почистить», «течёт»).
3. Сохрани файл — изменения подхватятся сразу.

Пример из разработки: жалоба «Кондиционер начал течь, вода капает»
сначала не находила раздел о ремонте — слова «течь» и «капает» после
стемминга не совпадали с «течет». В `keywords` раздела `faq-repair`
добавлены «течь», «протекает», «капает», «вода», «мастер», «срочно», и тест
`test_search_finds_relevant_item` закрепляет результат.

## 11. Типичные ошибки

| Симптом | Причина | Что сделать |
| --- | --- | --- |
| Сервер не запускается: `База знаний не загружена: JSONDecodeError` | Синтаксическая ошибка JSON при старте | Найти строку и столбец из сообщения, проверить запятые и кавычки |
| `/health` → `degraded` | Сломанная правка при работающем сервере | Исправить файл; до этого работает прошлая версия |
| `неизвестные id в related` | Опечатка в `related` или позиция удалена | Исправить `id` или убрать ссылку |
| Модель называет «цена не указана», хотя цена есть | Позиция не попала в найденные | Добавить синонимы в `keywords`, проверить «Источники» |
| Найдено слишком много лишних позиций | Слово встречается почти везде («кондиционер») | Нормально: у такого слова маленький IDF, оно мало влияет на порядок |
| Правка не видна в Docker | Файл правится не в `./data` проекта | Править `data/knowledge_base.json` рядом с `docker-compose.yml` |

## 12. Проверь себя

### Вопросы

1. Почему у «Демонтажа» `amount: null`, а не `0`?
   *Ответ:* `0` означал бы «бесплатно». `null` — «цена не фиксирована»;
   модель увидит пояснение из `note` и не назовёт число.
2. Что будет, если сохранить невалидный JSON при работающем сервере?
   *Ответ:* сервис продолжит работать на последней корректной версии,
   `/health` покажет `degraded` и текст ошибки.
3. Почему «сколько» и «стоит» — стоп-слова?
   *Ответ:* они есть почти в каждом вопросе и не помогают отличить один
   товар от другого.
4. Зачем склеивать «Бриз 18» в `бриз#18`?
   *Ответ:* чтобы число из площади («18 м²») не совпадало с номером модели.
5. Почему у монтажа оценка 2.803, а у кондиционеров 0.934 на вопрос про монтаж?
   *Ответ:* слово «монтаж» у первого в названии (вес 3), у вторых — только
   в условиях (вес 1); IDF одинаковый.
6. Зачем модели связанные позиции, если клиент про них не спрашивал?
   *Ответ:* это кандидаты для допродажи; без их фактов модель не смогла бы
   рекомендовать их с правильной ценой.

### Самостоятельное задание

Добавь в базу услугу «Установка защитного козырька» (`id`: `canopy`,
